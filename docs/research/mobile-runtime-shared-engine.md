# Mobile runtime and shared engine feasibility

Research date: 2026-09-06. Evidence for [research #24](https://github.com/0xRowdy/true-count/issues/24), informing [architecture #16](https://github.com/0xRowdy/true-count/issues/16). This note establishes documented capabilities and implementation constraints; it does not certify game correctness, recovery, or performance. Recommendations remain proposals until accepted in the architecture decision.

## Decision implication

Given the user's TypeScript preference, polished 2D tables, and iOS/Android launch, **React Native with Expo development builds and a portable TypeScript engine is the strongest starting proposal**. React Native documents Hermes execution; Expo supports native integration and local/cloud builds; Node supports headless JavaScript computation. These capabilities support sharing the rules implementation between practice and standardized simulation without translating it into a second language. This is an architectural inference, not a throughput result. [React Native environment](https://reactnative.dev/docs/javascript-environment), [Expo workflow](https://docs.expo.dev/workflow/overview/), [Node workers](https://nodejs.org/api/worker_threads.html)

Flutter/Dart and Kotlin Multiplatform remain technically viable. Neither is required by an identified capability gap. The accepted [offline lifecycle](../decisions/offline-access-subscription-lifecycle.md) makes durable recovery, pinned behavior, and access-time uncertainty responsibilities of the application in every candidate. Database/sync, authentication, subscription providers, numerical blackjack validation, and simulation capacity retain their separate decisions.

## Candidate comparison

| Candidate | Documented mobile/headless route | Relevant tradeoff |
| --- | --- | --- |
| React Native + Expo; pure TypeScript engine | Hermes on mobile; portable compiled JavaScript on Node. Expo development builds permit native libraries and custom modules. [RN](https://reactnative.dev/docs/javascript-environment), [Expo](https://docs.expo.dev/workflow/overview/) | Fits the preferred language. Sharing requires excluding React, Expo, Node-only modules, persistence, and device services from the engine. TypeScript source sharing is not a guarantee that every host API exists everywhere. |
| Flutter; pure Dart engine | Flutter targets iOS/Android; `dart compile exe` creates self-contained Windows/macOS/Linux executables. A package independent of Flutter UI can therefore serve a headless simulation runner. [Flutter iOS](https://docs.flutter.dev/platform-integration/ios/setup), [Flutter Android](https://docs.flutter.dev/platform-integration/android/setup), [Dart compilation](https://dart.dev/tools/dart-compile) | Viable shared implementation in another language. Native Dart integer semantics differ from Dart compiled to JavaScript, relevant to a later browser consumer. [Dart numbers](https://dart.dev/resources/language/number-representation) |
| Kotlin Multiplatform; shared Kotlin engine | Common source sets can target Android, iOS, JVM, and native executables; Kotlin/Native exposes Apple frameworks to Swift/Objective-C. A JVM or native runner can consume shared logic. [Project structure](https://kotlinlang.org/docs/multiplatform/multiplatform-discover-project.html), [Native overview](https://kotlinlang.org/docs/native-overview.html) | Viable, but requires Kotlin tooling and an explicit UI choice: native screens or shared Compose UI. Sharing logic alone does not select a shared UI. [KMP approaches](https://kotlinlang.org/docs/multiplatform-get-started.html) |

The engine should accept explicit commands, serializable state, immutable revisioned definitions, and explicit random state. It should return the resulting state plus structured settlement/coaching/explanation facts. Each host supplies storage, access decisions, scheduling, presentation, and native services. This proposed boundary follows the accepted need for identical interactive/automated semantics; it is not a framework feature.

## Computation and native integration

React Native normally runs business logic on its JavaScript thread. A long calculation can delay touch handling and JS-driven updates even while some native scrolling/animations continue. Declaring an operation asynchronous does not establish another execution thread. Keep ordinary engine transitions bounded; split long automatic settlement into resumable batches and yield between them. Measure release builds on target devices: React Native warns that development mode changes performance substantially. [React Native performance](https://reactnative.dev/docs/performance)

Node's `worker_threads` explicitly executes JavaScript in parallel and is intended for CPU-heavy work; its docs recommend pooling workers rather than creating one per task. This provides a documented headless execution route, not a mobile worker API. Assign independent simulation work and seeds deterministically so changing pool size does not change results. A separate mobile JS runtime/native compute integration would be additional engineering if profiling demands it. [Node workers](https://nodejs.org/api/worker_threads.html)

Flutter's main isolate also handles application/UI work; helper isolates allow concurrent computation with separate memory and messages. Spawned isolates cannot perform widget work or use `rootBundle`. Kotlin's `Dispatchers.Default` uses a shared thread pool on JVM and Native, providing an explicit place to schedule computation. In either design, serialize ownership of each activity's mutable state. Worker/isolate availability establishes scheduling options, not comparative speed. [Flutter isolates](https://docs.flutter.dev/perf/isolates), [Kotlin dispatcher](https://kotlinlang.org/api/kotlinx.coroutines/kotlinx-coroutines-core/kotlinx.coroutines/-dispatchers/-default.html)

Expo Modules can expose Swift/Kotlin capabilities to the app. Flutter platform channels connect Dart to native code and have thread rules, including background task-queue options. Kotlin uses platform-specific implementations behind common declarations such as `expect`/`actual`. These are suitable seams for platform clocks, lifecycle, and other device services; none requires moving game rules into native code. [Expo Modules](https://docs.expo.dev/modules/overview/), [Flutter channels](https://docs.flutter.dev/platform-integration/platform-channels), [Kotlin declarations](https://kotlinlang.org/docs/multiplatform/multiplatform-expect-actual.html)

## Exact arithmetic and reproducibility

ECMAScript `Number` represents safe integers only within ±(2^53−1). Validating stored inputs alone is insufficient: intermediate products, accumulated simulation totals, and payout calculations must remain exact too. For TypeScript, propose integer stake units and explicit rational payout/commission rules, with checked bounds and specified rounding; reject unsupported magnitudes before unsafe arithmetic. A decimal-looking amount is not automatically exact. [ECMAScript safe integers](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-number.max_safe_integer)

Hermes' current feature list explicitly includes `BigInt`; do not repeat the outdated blanket claim that Hermes lacks it. React Native ships a compatible Hermes version with each release, so verify the selected Expo/RN/Hermes combination rather than treating the repository's current feature list as a release matrix. If large totals require `BigInt`, test its operations on both Hermes and the selected Node version and define a canonical string/byte encoding: ordinary JSON serialization throws for an unconverted BigInt. No BigInt performance comparison was measured. [Hermes features](https://github.com/facebook/hermes/blob/main/doc/Features.md), [Bundled Hermes](https://reactnative.dev/docs/hermes), [ECMAScript JSON serialization](https://tc39.es/ecma262/multipage/structured-data.html#sec-serializejsonproperty)

Dart native `int` uses signed 64-bit representation, while Dart compiled to JavaScript uses double-precision numbers; native arithmetic assumptions therefore cannot silently carry into a future web build. Kotlin supplies fixed-width integer types, but integer operations can overflow without an automatic compiler error. Wider integers increase the available range; they do not remove the need to bound and test payouts, progressions, counters, and aggregates. [Dart representation](https://dart.dev/resources/language/number-representation), [Kotlin overflow](https://kotlinlang.org/docs/numbers.html#data-overflow)

`Math.random()` uses an implementation-defined algorithm and offers no seed parameter. Dart's seeded `Random` stream may change between library releases; Kotlin guarantees seeded repeatability within the same runtime version and warns that future algorithms may differ. Consequently, none of these default APIs alone is a durable cross-version replay contract. [ECMAScript random](https://tc39.es/ecma262/multipage/numbers-and-dates.html#sec-math.random), [Dart Random](https://api.dart.dev/dart-math/Random/Random.html), [Kotlin Random](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin.random/-random.html)

Proposed application contract: pin a named RNG algorithm/version, seed encoding, complete resumable state, draw order, bounded sampling/shuffle behavior, and game/rule/strategy/reference versions. Preserve already-generated outcomes; version labels without retained executable behavior cannot reproduce them. Keep rendering, explanations, retries, and worker scheduling from accidentally consuming the game stream. Specify serialization order, integer conversion, rounding, and unsigned/overflow behavior and verify shared vectors in actual mobile and headless runtimes. Statistical RNG suitability and numerical blackjack reference correctness require their own evidence; this investigation chooses no algorithm.

## Restart and update recovery

Android's documentation distinguishes transient UI state from persistent application data and explicitly says ViewModel/saved-state mechanisms do not replace local storage across restarts. A corresponding architectural conclusion applies to all candidates: persist the game activity, not merely the screen or in-memory engine instance. [Android state persistence](https://developer.android.com/topic/libraries/architecture/saving-states)

To satisfy the accepted lifecycle, propose an atomic durable transition containing generated outcomes/random position, outstanding wagers, resolved payouts, pending strategy actions, revision identities, answers/assistance/deviation flags, and allowance effects. Associate commands/accounting effects with stable identifiers. A retried pending adjustment must read the already-settled outcome instead of paying it again. Expose a transition as committed only after its recovery record is durable. Actual transaction implementation and failure injection remain unproven; this defines the storage boundary without choosing a provider.

Expo `runtimeVersion` matches a JavaScript update to a compatible native binary. It does **not** specify True Count's engine version, state schema, rule/reference bundle, or behavior retained for an unfinished activity. Native changes need a new binary. Expo also warns that rolling an update back can fail when persistent state changed incompatibly. Update delivery is therefore separate from game-data compatibility, and EAS Update is optional rather than selected by this note. [Runtime versions](https://docs.expo.dev/eas-update/runtime-versions/), [Update recovery](https://docs.expo.dev/eas-update/error-recovery/)

For every stack, a release must include the behavior/data needed by retained active revisions or a validated migration preserving the accepted semantics and fixed outcomes. A migration must not reroll or reinterpret a paid result. Preserve recoverable history and mark an activity incomplete when valid recovery is impossible, as already accepted. Plan forward and rollback compatibility, engine/reference retention and retirement, and offline upgrade tests; keeping the new version alone is insufficient. These are application obligations inferred from the lifecycle, not an assertion that any updater automatically keeps old engines.

## Elapsed time and build constraints

Android `SystemClock.elapsedRealtime()` includes deep sleep and measures time since boot monotonically; the displayed wall clock can jump, and `uptimeMillis()` excludes deep sleep. Apple's public `mach_continuous_time()` advances during sleep and is declared available on iOS in Apple's Mach header. These support native elapsed-time adapters for expiry checks. [Android clocks](https://developer.android.com/reference/android/os/SystemClock), [Apple clock semantics](https://developer.apple.com/documentation/driverkit/mach_continuous_time), [Apple public header](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/mach/mach_time.h)

A monotonic counter is not, by itself, a persistent proof that two readings span the same boot. Comparing only whether the new reading is lower cannot detect every reboot. Proposed access adapter: retain the trusted online deadline/anchor, use validated sleep-inclusive elapsed time only while continuity is established, and return uncertainty when it cannot be established. Reconnection then follows the accepted policy; it must not create a fresh grant or prevent permitted final settlement. Boot continuity across process termination and OS updates needs platform verification. This research does not establish a tamper-resistant offline clock or a reliable cross-reboot identifier.

If an implementation uses Apple's listed boot-time APIs such as `systemUptime` or `mach_absolute_time`, their required-reason declarations and restrictions must be checked for the selected use. The cited list does not justify claiming that every monotonic API has identical requirements. [Apple accessed API reasons](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitype)

Expo permits local native builds or cloud builds, and custom native code requires a development build rather than Expo Go. Local iOS build/debug uses Xcode; Flutter likewise documents Xcode and native plugin tooling, and Kotlin/Native Apple targets require Apple's tools. Linux can host shared-engine and Android work; an iOS native build/test path still needs Apple tooling locally or on an appropriate build host. No cloud-build provider, signing setup, or minimum OS version is selected here. [Expo workflow](https://docs.expo.dev/workflow/overview/), [Flutter iOS setup](https://docs.flutter.dev/platform-integration/ios/setup), [Kotlin Native setup](https://kotlinlang.org/docs/native-get-started.html)

A separate Rust/native engine is possible but introduces another language, platform binaries, bindings, ownership/lifetime and error conventions, and integration tests. Rust's FFI guidance explicitly covers these boundary responsibilities. Adopt it only for a demonstrated requirement or measured bottleneck sufficient to justify the added build/distribution surface; assumed speed is not evidence. [Rust FFI](https://doc.rust-lang.org/nomicon/ffi.html)

## What still requires implementation evidence

The finite acceptance work is cross-runtime deterministic vectors; release-device responsiveness with long settlement tails; native time continuity/uncertainty scenarios; and restart/upgrade/rollback failure injection proving unchanged outcomes and exactly-once accounting effects. Source review establishes plausible routes for these checks. No executable engine, benchmark, native-clock spike, or recovery proof was produced in this investigation. Backend capacity and numerical coaching validation remain outside this research ticket.
